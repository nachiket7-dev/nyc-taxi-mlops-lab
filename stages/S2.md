# S2: model pipeline (Day 1, 15:00–16:30)

**Goal:** the pipeline trains a model on a window of months, registers it in MLflow, and compares it with what's serving on the same holdout. Only a version that beats it, within the latency budget, becomes `challenger`. No person and no notebook sets that alias by hand.

## Recall check (5 minutes, no agent)

1. What is target leakage? Give one example from a taxi trip record.
2. Why evaluate on the month after the training window rather than a random split of the same months?
3. MAE or RMSE for trip durations, when a few trips take three hours? What does each reward?
4. What does an MLflow alias give you that a version number doesn't?

## Given

- `contracts/features.yaml` (inputs, label, forbidden post-trip columns) and `contracts/mlflow.yaml` (names, aliases, metrics, version tags). Frozen.
- `tripmodel` (`pipelines/src/tripmodel/`): v1 baseline (median per zone pair and hour), v2 LightGBM, the zone-pair distance lookup both carry, and `evaluate` (MAE, slices, p95 latency). No Dagster, no AWS: serving uses it too.
- `trip_features` (Dagster asset): one month of inputs and labels in `staging.trip_features`.
- MLflow on the platform host (already in `deploy/compose.platform.yaml`): runs in RDS, artifacts in your bucket. Open it with SSM port forwarding on port 5000.
- `infra/modules/notebook` and `notebooks/explore.ipynb`: a SageMaker notebook with the backstory, the data and three models side by side.

## Build

1. **Notebook:** set `github_repo` in `infra/live/terraform.tfvars`, wire `infra/modules/notebook` into `infra/live/notebook.tf` (it must reach MLflow on port 5000), apply (about 5 minutes). Open it (SageMaker console → Notebook instances → Open JupyterLab) and run `explore.ipynb`.
2. **Features:** add `trip_features` to your ingest job, write the `feature_contract` check (`pipelines/src/labpipes/defs/feature_check.py`), then materialize `trip_features` for 2024-01..04.
3. **Training** (`training.py`): `training_set` (UNLOAD the window and holdout to your bucket), `trained_model` (fit v2, log and register it with the tags `mlflow.yaml` lists), `eval_report` (new version vs the champion, or the v1 baseline before there is one), a blocking gate, and a `challenger` asset that sets the alias. Run `train_model` from the Dagster UI, or `scripts/dagster-run.sh train_model`.

## Decision points (one record each in `decisions/`)

- **What stays in the notebook** and what moves into the pipeline.
- **Promotion metric and margin:** what must a new version beat, and by how much?
- **Training window:** which months train, which month tests, and why.

## Done when

- `make check` passes, and the platform workflow is green.
- `trip_features` has 2024-01..04 with `feature_contract` passing; `eval_report`'s gate passed.
- In MLflow, `trip-duration` has a version carrying every tag in `contracts/mlflow.yaml`, and `challenger` points at it.
- The status workflow has run since (the grader reads it).
- Your three new decision records exist.

## Last 15 minutes: a colleague's change

Once your `challenger` is set, your instructor hands you a patch file: a colleague's change that claims a much better model. You own this repo, so you decide whether it goes in.

1. On a new branch, apply it: `git switch -c colleague-model && git apply <patch file>`.
2. Review the diff the way you would at work, before running anything. Ask yourself what the model will be given when it is serving a real request, not what it was given in the colleague's notebook.
3. Decide: merge, ask for changes, or reject. Write your verdict and the reason in two or three sentences (the commit message, or a note in the repo). Be ready to defend it.
